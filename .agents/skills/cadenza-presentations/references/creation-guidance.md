# 创建引导

## 产品迭代原则

- CadenzaSlide 的目标是可跨主题、内容结构、信息密度和页面类型复用的 Skill、方法论、组件工厂、Composer 与 Verifier，不是一份固定 Demo。
- Demo 只作为代表性输入、问题探针和回归样例。不得以单份 Demo 好看证明系统成立，也不得依赖只对该 deck 有效的逐页手工修饰。
- 默认闭环是：选择代表性输入 → 用当前系统生成 → 在真实画布观察 → 把问题提炼为可复用规则、组件能力、生成逻辑或 verifier 契约 → 强化系统 → 对原案例与不同案例重新生成和验证。
- 每轮反馈都必须回答“如何让下一次同类输入自动做对”。可复现、可推广或可预防的经验必须进入系统；只有真正依赖特定事实且无法泛化的调整才留在单个 deck。
- 成功标准是同一套方法能稳定跨场景产出、保持 Cadenza 调性，并在交付前发现和纠正失败结果；Demo 完成度只是一项证据。

新建 deck 时，把 Agent 当作演示顾问，而不是表单。先复用用户已经提供的信息，再按风险选择路径；不要让每个请求都经历完整访谈。

## 选择路径

- **快速路径**：目标、观众、素材和交付规模已足够清楚，或用户只要低成本草稿。简要复述 creation contract，对非关键缺口记录假设，随后进入素材分析和 outline。
- **引导路径**：董事会、融资、客户提案等高风险场景，或核心目标、观众、依据、交付规模仍会实质改变结果。每轮只问最多 3 个高杠杆问题；能从上下文、附件或 workspace 得出的内容不要重复询问。
- 不要求用户先选择路径。根据请求判断，并允许用户随时说「按你的假设继续」或要求更深入讨论。

## 五阶段收敛

五阶段是检查清单，不是五轮固定问答。只对会改变结果的未决项暂停。

1. **Strategy**：明确观众、使用场景、演示目标、希望观众最终相信或采取的行动。
2. **Substance**：确认可用素材、权威来源、时效范围、必须保留的事实与缺失证据。用户提到但未提供关键文件时先索取文件，不要凭空替代。
3. **Structure**：确认时长、目标页数范围、屏幕比例、重点章节、结论先行与否及结构方向。只有时长时，说明节奏依据后再确认页数范围。
4. **Design**：识别用户提供的品牌、模板或视觉参考；没有参考时由 deck-local master 负责视觉方向，不向用户抛出颜色、字体、layout 等低价值选择。
5. **Build**：先生成可审阅 outline 并等待用户明确确认；确认后再填充完整内容、notes、图表和视觉。

## Creation contract

进入素材分析前，用一段紧凑摘要向用户确认：

- 主题与核心结论
- 目标观众、场景与期望行动
- 演讲时长、目标页数范围和屏幕比例
- 素材范围、数据时效与必须引用的来源
- 重点章节、结构方向与明确禁区
- 已授权 Agent 决定的事项及其假设

不要逐字段机械提问。用户纠正其中一项时，只更新受影响的契约内容。

## Outline checkpoint

outline 必须让用户能在昂贵的完整生成前发现叙事问题。除稳定 slide ID 与标题外，每页至少展示：

- 每页一句话主张
- 该页的叙事作用
- 预期使用的证据来源或明确标记「待补证据」

同时给出总页数、章节分组和预计节奏。把完整 outline 紧接在执行队列之后展示，不要只给任务名称而隐藏页面结构。随后等待用户明确确认，不把沉默视为同意。用户调整顺序、删页或改主张时，只更新 outline；确认前不得开始完整页面构建。

## 可观察的执行队列

当完整构建预计包含多个工具步骤、资源处理或超过约 8 页时，在开始前使用可用的 host-native plan 展示 3–7 个结果导向的任务。典型队列为：

1. 规划结构并创建 deck 骨架。
2. 完成图片、数据或引用等资源准备。
3. 按连续页码或章节分批构建内容页；按实际规模拆成一批或多批。
4. 分别执行技术验证与视觉验证，修复后复验。

任务名称要写清产物和范围，例如「构建 01–08 页」或「处理已选用的 12 张图片」，不要写成含糊的「继续处理」。同时只有一个任务处于进行中；完成一批就立即更新状态并说明产物，不要等全部结束后一次性补报。范围变化时同步修订后续任务。

执行队列是透明度机制，不是装饰：不要虚构进度、百分比、预计耗时或尚未发生的验证结果。简短 deck 或单页修改不强制创建队列。

## Build 与迭代反馈

- outline 确认后再启动资源转换和分批构建；素材读取与结构分析可以在确认前完成。
- 为每页读取 deck-local master 的 authoring profile，并按以下顺序选择：
  1. `complete`：专用母版已完整表达 slide intent，直接成页；不得为了填满页面添加无意义装饰。
  2. `startup`：先判断基础内容是否已经足够；足够时记录 `base-sufficient`，需要数据、关系、证据或媒体时才在兼容 region 中组合内容并记录 `composed`。
  3. `canvas`：只有 complete 与 startup 都无法表达时才选择，并记录 `justified-canvas`；不得仅为获得自由坐标而使用 `blank`。
- 每批在 host-native 执行记录中列出 slide ID、layout、authoring path 与理由。该记录用于解释 Agent 决策，不得写入第二份 deck 内容；`deck.cadenza.json` 仍是唯一内容来源。
- 生成期间用面向成果的短更新说明当前完成到哪一阶段、产物在哪里、下一检查点是什么；不要倾倒内部工具日志。
- 每批写入后做轻量确定性检查；全部批次完成后再运行完整 `verify --browser`，以及真实 Audience viewport 的视觉检查。
- 完成后先报告 file/browser verify 结果，再打开 Overview 供用户做叙事和视觉判断。
- 后续修改优先使用稳定 slide ID。用户跨多页批注时可合并为一批，但逐项核对结果；不要为每次修改复制整个 deck。

## 原子组件组合路由

不要从组件名称或视觉偏好开始。每页先把内容声明为稳定 ID 的信号：主张、证据、指标、顺序、媒体、来源和真实关系。缺失信号保持缺失，不得为了某种图形补造增长率、目标、人物、阶段、责任方或连接。

production registry 只有三类可组合原子：

- `layout`：`stack`、`cluster`、`grid`、`split`、`inset`、`overlay`，只负责父子结构、slot、顺序、比例、方向、密度和受控强调。
- `content`：`heading`、`copy`、`metric`、`list`、`card`、`quote`、`media`、`profile`、`logo`、`caption`，每个组件只表达一种内容角色。
- `relationship`：`divider`、`connector`、`progress`；`connector` 的端点必须引用同一 composition 中真实存在的 node ID，`progress` 必须有用户提供的数值。

`metric.hero`、`collection.cards`、`process.swimlane` 等 25 个旧表达是已失败的宏观抽象，不得用于新 authoring，也不得通过换名继续进入 Gallery。少量明细仍可使用原生 table，数据图交给独立 chart adapter。

同页只保留一个主构图。优先通过父级 layout 改变同一 content renderer 的关系，不在 content 组件内部预埋页面模板。不要用等大的 card 网格填满页面；容量超限时先使用结构化拆页建议，`compact` 只能由 diagnosis 触发一次，不能主动当作视觉风格。

## Composer 与复核闭环

1. 从 production registry 生成多个有限 composition tree，不生成内部坐标。
2. 按 `signals → slots/parent → capacity/intrinsic → profile budget → tokens → fidelity` 做硬过滤；失败候选不进入排序。
3. 为合法候选生成解释、composition fingerprint 和确定性分数。seed 只在语义分差接近时改变候选顺序；相邻页重复惩罚也只能作用于等价候选。
4. 写入 `kind: "composition"`、稳定 `compositionId`、外层 master region `frame` 和已验证 `tree`。无合法树时返回 repair/simplify/split，不得写入半成品 JSON。
5. 在 Audience 全尺寸检查主张、事实覆盖、阅读顺序、连接、字号、边界、主次和 Cadenza 调性。结构断言通过不代表审美通过；出现空洞、背景吞没标题、重复 chrome、主次不明或后台卡片墙时必须重新组合或拆页。
6. 横向 `split` 用于前后、方案或同级对比时，两个 slot 的首要内容必须共享起始基线。优先让两列结构同构；若结构不同，使用 `alignment: start`，并把跨列 `connector` 放在共同父级，不能只塞入一侧导致整列下移。
7. `grid` 中同一行的同类内容必须共享上下行基线；`divider` 只在存在真实语义分隔时使用，不得把带标签的线当作标题或空白填充物。

## 生成前的画布利用约束

- Cover（`role: intro`）与 Section 可使用有意图的负空间；其他页面必须让主构图占据主要可用区域，且内容本身与容器容量匹配。组合页在 1280×720 Audience 中应达到至少约 35% 的真实内容面积，并让有效内容覆盖至少约 60% 的纵向行；这两个指标是发现问题的最低门槛，不是鼓励机械填满。
- “容器面积大”不等于“内容覆盖率高”。禁止用空卡片、空列、空白 split slot 或拉满高度的短列表骗过页面覆盖；短内容应让容器收缩、改变关系或拆掉容器。
- 大型 card、metric 或 profile surface 内若只有少量顶部文字，视为无效覆盖。优先补足真实证据或改用 heading/list/cluster 等更贴合容量的结构，不得添加装饰性假数据。
- 短内容进入大 surface 时必须选择一种明确策略：有依据地补充真实内容；使用 `density: open` 让 Renderer 以更大但有层级的字号居中呈现；或收缩容器／更换关系。禁止把短文字贴在大容器顶部并把剩余空白伪装成“填满”。
- 功能或机制说明只有少量证据时，先检查主张中是否已经包含输入、处理、输出或门禁等真实阶段；可以把这些已有语义拆成编号阶段卡形成阅读路径，但不得为了凑满画面补造步骤。两张短卡在大区域内彼此孤立时，应改成阶段结构、明确关系或收缩区域，不能靠放大空卡维持版面。
- 视觉平衡按实际视觉重量判断，不以几何居中代替构图。大数字、长引言、亮色纸面和高对比纹理都属于重元素；辅助说明、署名或次级信息必须通过共同轴线、横向展开、视觉咬合或明确承托关系与主元素组成一个整体。对角线天然表达运动、方向、冲突或不稳定张力，只有内容确实包含这些语义时才可使用；不得为了填补空白把静态原则页拆成无意义的斜向反重心。禁止让主元素居中悬浮、说明条孤立下挂，或把全部重量压在同一象限后把其余区域称为留白。核心母版必须通过 `master.visual-balance`，并在 Audience 全尺寸复核真实文字墨迹而非只看 slot frame。
- 标题、引言与说明文字不得依赖额外的半透明或不透明纸片托底来制造层级。文字应直接落在画布、媒体或有真实语义的实体容器上；标题层级使用字号、位置、字重、线条或结构分区表达。`title-box` 等标题 wrapper 的背景必须透明，除非该容器本身就是输入内容明确要求展示的实体对象。
- TRACK、ORBIT、HALO 等高对比背景必须通过 `visualRegions` 声明主要纹理或运动路径；标题、正文和必须读取的说明槽必须落在明确的安全区，不能与高密度路径相交。修复冲突时应移动或重构内容与背景关系，禁止用半透明或不透明纸片遮住背景。TRACK 尤其应让轨道从主体下方或侧后方经过，不能横切标题字面。
- 母版构图遵循“脚踏实地 → 主体明确 → 留白适量 → 节奏与重复”的顺序：主体和辅助信息先共享可辨认的基线、边缘或承托关系；主张必须成为第一视觉焦点；留白应围绕阅读路径分布且不能形成大面积失重空洞；最后才通过一致的间距、线宽、字号梯度或相似形态建立节奏，并只保留足以形成系统感的重复。不得用装饰块、孤立底板或随意错位伪造节奏。
- 写入 deck 后先运行静态 `verify` 检查 `layout.content-coverage`，再运行 `verify --browser` 检查真实渲染中的 `browser.content-coverage`、`browser.empty-surface`、`browser.region-balance`、`browser.text-clipping`、`browser.orphan-line`、`browser.split-alignment` 与 `browser.peer-alignment`。整页合格但主要 Split slot 仍然偏顶或偏底时，`browser.region-balance` 必须失败；任一 finding 都必须回到内容或系统层修复后复验。
- 中文标题与正文不得留下 1–2 个字的孤立末行。优先重写文案或显式 authored line break；不得只靠缩小字号掩盖问题。
- Cadenza 的标题、卡片、列表、图注与说明性正文默认不以中文或英文句号收尾；只有明确的 Quote 引言正文可保留。静态 `verify` 的 `copy.terminal-period` 必须在交付前清零。
- Connector 带有关系标签时，它是演示内容而非装饰：全尺寸 Audience 中标签不得低于 14px，并应保留足以辨认方向和关系的线长。无语义装饰线应使用 Divider，不得用不可读的小字伪装 Connector。
- Divider 只用于表达真实的语义分段或组间边界。不得给 Divider 添加看似标题的标签来填补空白，也不得用它替代 Heading；没有独立分隔关系时应直接省略。
- Grid 中同一行的同类 Card、Metric、Profile、Quote 或 List 是一个可比较集合，必须共享顶部与底部行基线。不得让每个 peer 按自身高度分别居中；`browser.peer-alignment` 必须在全尺寸渲染中检查两端误差。
- 当一个主张同时统领左右两组证据时，应把共享 Heading 放在 Split 上方，再让两个证据区从同一基线开始；不得把共享主张塞进其中一栏，造成另一栏无缘由地上浮。若主要 Split 区只有一个可伸展的 List，应使用 `density: open` 让真实条目形成覆盖整个分区的纵向节奏，不能把短列表贴在顶部留下失重空洞。
- 小字号只允许承载 eyebrow、编号、来源和辅助 metadata；主张、正文、列表项、Card body、Profile bio、Progress label 与关系标签都属于必须读取的信息，必须通过 `browser.semantic-type-size` 的角色化字号门槛。不得用“画面上存在”替代“观众能读到”。
- Master 固定层、页脚、装饰条以及 `::before` / `::after` 伪元素不得进入内容安全区或压住文字。`browser.layer-collision` 必须使用真实渲染矩形检查跨层遮挡，不能只依赖元素自身的 overflow。
